# AI 면접관 P0 실행·검증 결과

검증일: 2026-11-02 · 대상: 기존 `/interview`의 자료 로딩·질문 검수·평가·복구 경로

후속 변경: 이후 실시간 호출 체인을 사전 Q0 은행과 단일 코어로 전환했다. 아래는 당시 P0 실행 기록이며 최신 구조·검증 범위는 [단일 코어 전환 및 최신 로그 검토](면접_단일코어_전환_및_최신로그_검토.md)를 기준으로 확인한다.

요청한 순서대로 **경로·원문 검증을 먼저 통과한 뒤**, 질문 전제 검수 → 최신 평가 집계 → 복구 회귀를 실행했다. 화면 디자인은 변경하지 않았다. 이 문서는 [개선 로드맵](AI_면접관_성능_개선_로드맵.md)의 실행 후 상태이며, 모든 P0 완료를 뜻하지 않는다.

## 2. Step 1 — 실제 자료 경로와 Source Manifest

경로와 정본 버전을 `interview-files.mjs`에 모았다. `interview.config.ts`, 데이터 로더, PDF 준비 스크립트가 같은 계약을 사용한다.

| 역할 | 실제 경로 | 정본 |
|---|---|---|
| 학생부 | `래퍼런스/윤지우학생 생활기록부.pdf` | 실제 24쪽 PDF |
| 공통 운영 | `각자의답_MD/8. 면접엔진_공통운영원칙_v2.0.md` | v2.0 |
| 질문 | `각자의답_MD/9. 면접엔진_질문생성_가이드라인_v2.3.md` | v2.3 |
| 평가 | `각자의답_MD/10. 면접엔진_답변평가_가이드라인_v2.3.md` | v2.3 |
| 지원처 | 루트 `universities.json`, `departments.json`, `admission_tracks.json` | 대상 ID·2027학년도·전형 대조 |
| 발췌 캐시 | `data/prepared/student.json` | `verified-pdf-excerpts-v2` |

`npm run verify:context`에서 다음을 확인했다.

- 필수 8개 파일을 읽고 해시를 기록했다. 오류는 0개다.
- MD 첫 제목의 **문서 역할과 버전**을 함께 확인한다. 같은 v2.3인 질문·평가 문서를 바꿔 연결해도 통과하지 않는다.
- 실제 PDF 바이트의 SHA-256과 캐시·각 근거의 PDF 해시를 대조했다.
- 실제 PDF에서 페이지를 다시 추출해 17개 근거의 파일·페이지·offset·본문·전체 페이지 수를 대조했다. 해시만 일치하고 캐시 본문이 바뀐 경우도 차단한다.
- `pdfHashVerified`, `evidenceReferencesVerified`, `evidenceTextVerified`가 모두 `true`다.
- 지원처의 공식 면접 시간은 720초로 유지했다. 시간당 주질문 수는 기존 서비스 정책이며 공식 문항 수로 표시하지 않는다.

Source Manifest는 `local-interview-source-manifest-v3`이며 공통 2.0, 질문 2.3, 평가 2.3을 기록한다. 정본을 읽었다고 정본의 모든 고도화 항목이 구현된 것은 아니다.

분석 대상 원본 MD 30개는 이전 분석 시점의 SHA-256과 다시 대조했으며 변경이 없다. 입력 문서를 수정해 검증을 통과시키지 않았다.

주요 파일: `interview-files.mjs`, `interview.config.ts`, `scripts/prepare-context.mjs`, `scripts/verify-interview-context.ts`, `server/data/load-interview-context.ts`, `server/data/verify-student-source.ts`.

검증 증거: `artifacts/p0-step1-verification.txt`, `tests/source-integrity.test.ts`, `tests/school-context.test.ts`. 페이지 끝을 초과하는 offset 차단 반례를 포함해 자료·학교 관련 테스트 총 17개 통과.

## 3. Step 2 — 질문 전제·평가·복구

### 질문 전제와 단일 의도

질문 생성 후 인용·계획·발화 검사를 거쳐 **독립된 검수 호출이 최종 질문을 승인해야 TTS를 준비**한다. 같은 설정 모델을 별도로 호출하는 방식이며, 다른 모델의 합의나 사람 검수는 아니다.

- 원문·확정 답변에 없는 개인 역할·성과·수치·인과·책 제목을 사실로 전제하는지 확인한다.
- 질문에 포함된 주장과 검수 인용이 실제 질문·출처의 정확한 구간에 붙는지 확인한다. 숫자와 단위 변경도 검사한다.
- 실제로 확인되지 않은 역할은 열린 확인으로 묻고, 가정은 가정으로 표현하도록 검수한다.
- 한 질문의 핵심 의도가 하나인지, 재진술이 원래 질문의 의도를 지키는지 확인한다.
- 승인되지 않은 질문은 기존 생성 재시도 상한 안에서 재작성한다. 불확실한 전제를 승인으로 바꾸지 않는다.
- 질문 해시·출처 ID·구간·승인 정보와 `premiseReviewMs`를 세션에 보존한다. 검수 metadata에 원문 답변을 중복 저장하지 않는다.
- 평가용 꼬리질문 상한은 설정·계획·프로토콜에서 모두 2회로 맞췄다.

주요 파일: `server/providers/question-premises.ts`, `server/providers/question-grounding.ts`, `server/providers/openai.ts`, `server/realtime.ts`.

**실제 모델 검증에는 남은 문제가 있다.** 8개 사례에서 예상 결과 7개가 일치했다. 근거 없는 전제·복수 요구 5개는 모두 차단했고, 정상 기록 확인과 열린 역할 확인은 승인했다. 정상으로 기대한 비교 질문 1개는 `PREMISE_UNCERTAIN`으로 과잉 보류됐다. 이후 원문에 명확히 연결한 비교 사례는 승인됐으나, 최초 실패를 해결한 것으로 계산하지 않았다. 더 빠른 reasoning 설정 실험도 5개 중 4개만 일치해 채택하지 않았다.

### 평가 집계와 근거 연결

회차 평가의 분모를 준비된 질문 목록에서 **실제로 제시된 질문의 재생 기록**으로 바꿨다. 브라우저 journal의 고유 clock ID와 시작·완료·중단·오류를 별도 장부에 저장하고 종료 요청의 백업 이벤트를 반영한 뒤 평가한다.

- Q0만 있으면 100%, F1까지 있으면 70:30, F2까지 있으면 70:15:15로 계산한다. 묶음 중간에 임의 반올림하지 않는다.
- Q0/F 중 평가불능이 하나라도 있으면 해당 묶음 전체를 보류한다. 남은 답변에 가중치를 재분배하거나 기술 실패를 0점으로 채우지 않는다.
- 유효 묶음이 **2개 이상이고 전체의 60% 이상**이어야 회차 점수를 낸다. 유효 묶음은 동일 비중으로 평균한다.
- 시작 후 실패·일부 재생·clock 충돌·질문 레코드 유실은 유효한 정상 제시로 인정하지 않는다. 원질문 레코드가 사라져도 시작 증거가 있으면 분모에서 숨기지 않는다.
- 서버가 답변 수집을 관찰했는데 재생 장부가 없으면 해당 묶음을 보류한다. 재생하지 않은 준비 후보는 분모에 넣지 않는다.
- 순수 재진술은 별도 평가용 F로 세지 않으며 원질문 답변과 연결한다. 이전 회차에 재생 장부가 없으면 관찰값을 만들어내지 않고 종합 점수를 보류한다.
- 채점에는 질문 의도·표적·깊이와 확정 답변의 실제 인용이 필요하다. 인용을 찾았다는 사실이 앵커 의미의 타당성까지 증명하지 않으므로 `semanticSupportIndependentlyVerified: false`를 명시한다.
- 개념 정오의 독립 검증 자료 부족에 따른 보류와 핵심 오류 상한의 비활성 상태를 그대로 보존했다.

주요 파일: `server/providers/evaluation-aggregation.ts`, `server/providers/openai.ts`, `server/question-presentation.ts`, `server/protocol.ts`, `lib/interview/client-events.ts`.

### 복구 회귀

실제 서버 경로에 격리된 합성 provider·클라이언트 이벤트를 연결해 다음을 자동 검증했다. 합성 전사를 실사용 기록이나 실제 브라우저 재생으로 간주하지 않는다. 자료 로더의 PDF 검증은 실제 PDFjs 경로를 사용한다.

- 중단 후 같은 answer ID로 재연결해 원래 확정 전사와 반복 발화를 보존한다. 오디오 청크 중복 소비를 막는다.
- 질문 TTS 실패 후 같은 예약 턴으로 재시도하고 중복 요청에는 캐시된 같은 턴을 반환한다.
- 재생 중단·종료 이벤트를 반영한 뒤 다음 답변이 확정되는지 확인한다.
- 완료되지 않은 재생, 중복 백업 이벤트, clock 충돌, 생성만 된 다음 후보가 정상 제시·평가 분모를 꾸미지 못하게 한다.
- 반응 형식 실패·재확인·전환의 기존 복구 및 비평가 재질문 계약을 함께 회귀했다.

증거: `tests/realtime-recovery.test.ts`, `tests/fixtures/realtime-providers.ts`, `tests/question-presentation.test.ts` 및 관련 반응·전사 회귀. 복구 관련 묶음 24개 통과.

실제 평가 호출에서는 70:30 묶음과 Q0 100% 묶음, 유효 2/2, 종합 점수 생성 및 축별 인용의 원문 결합을 확인했다. 사람 채점과의 일치도나 점수의 의미 타당성을 확인한 시험은 아니다.

실제 HTTP 준비 시험은 검수한 최종 질문의 해시·승인·검수 지연이 세션에 보존되고 MP3 바이트가 제공되는지 확인했다. 재생하지 않은 시험이므로 재생 장부는 비어 있어야 하며, 종료 후 `N_total=0`, 회차 점수 `null`을 확인했다. 이 새 시험 세션에는 합성 시험·장치 미사용·브라우저 재생 미측정을 명시했고 기존 사용자 회차는 덮어쓰지 않았다.

## 5. 지연과 다음 검증 게이트

이번 변경은 전제 신뢰성을 높였으며 **속도 개선으로 보고하지 않는다.** 실제 검수 8사례의 별도 검수 시간은 약 3.3~11.5초였다. 실제 질문 생성 시험은 총 17.5초 중 검수 6.3초, HTTP 준비 시험은 총 16.6초 중 검수 6.7초였다. 실제 평가 호출은 23.6초였다. 소수 호출의 관찰값이며 p95나 실제 사용자 체감 지연 통계가 아니다.

다음 검증은 정상 비교 질문의 과잉 보류를 줄이되 허위 전제 차단을 유지하는 것, 승인된 사전 질문 후보로 검수 비용을 앞당기는 것, 실제 장치로 다음 답변까지 이어지는 복구를 확인하는 것이다. 독립적인 채점·코칭 의미 검증과 새로고침·서버 재시작 후 동일 회차 복원도 남아 있다. 후속 질문의 주장 기억·전략 선택 등 P1 개선은 이번에 완료한 것으로 표시하지 않는다.

새 클라이언트의 clock ID·재생 장부 계약을 적용하려면 실행 중인 면접 화면을 새로고침하고 새 회차를 시작한다. 실행 주소는 `http://127.0.0.1:3000/interview`이며 서버는 새 빌드로 실행 중이다.
