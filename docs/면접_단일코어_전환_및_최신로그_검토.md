# 면접 단일 코어 전환 및 최신 로그 검토

기준일: 2026-11-02 · 범위: 기존 AI 면접 화면과 자료 준비·실시간 대화·종료 평가 엔진

기존 반응기 → 질문 생성기 → 별도 전제 검수의 실시간 호출 체인을 **사전 준비 / 단일 실시간 코어 / 종료 평가**로 전환했다. 새 화면·계정·SQL·업로드 기능은 추가하지 않았다. 기존 로컬 저장소에 출처가 검증된 활동 자료와 질문·음성 은행을 준비한다.

## 1. 최신 실사용 로그의 실제 문제

합성 검증 회차를 제외한 최신 기록을 확인했다. 질문을 생성한 기록과 실제 브라우저에서 재생한 기록을 구분했다.

| 회차 | 관찰한 사실 | 개선 방향 |
|---|---|---|
| `c4e524bb…` | 사과 뒤 비평가 재질문 분기는 맞았지만 제출→질문 재생 22.750초. 연결 발화 종료 뒤 공백 19.279초. 질문 준비 21.886초 중 전제 검수 12.987초·2회. 다음 무응답 전환에서 두 번 준비 실패 | 원래 승인 질문의 안전한 재제시, Q0 사전 준비, 실시간 추가 생성·검수 호출 제거 |
| `51d7e6a4…` | 사과 반응 뒤 약 17.8초 기다린 후 질문 준비 실패. 재질문 실제 재생 없음 | 대화 중 후보 재생성 비용 제거와 내부 원인 기록 |
| `ef48a5ad…` | 확정 전사 “같은 ”을 실질적인 주장으로 받아들여 `partial/probe`, 의미 없는 키워드 연결 멘트 생성 | 불완전한 파편을 비평가 재확인으로 분리 |

`ef48…`의 STT 이력에도 긴 답변이 있었다가 삭제된 증거는 없다. 약 13.7초 동안 인식된 내용은 해당 단어뿐이었다. 사용자의 원래 의도를 복원했다고 주장하지 않는다. 최신 세 회차에서 실제 평가용 F 재생은 0개이므로 이 기록만으로 꼬리질문의 내용 품질을 평가할 수는 없다.

당시 비공개 로그에도 `PROVIDER_ERROR`만 남은 실패가 있어 내부 원인을 확정할 수 없었다. 새 기록에는 코어의 timeout·형식·provider 실패, 출처·분기·검수 단계와 지연을 구분해 남긴다. 사용자에게 공급자명이나 내부 오류 코드를 노출하지 않는다.

## 2. 실행 구조

```text
사전 준비 — 자료/규칙/목소리가 바뀐 경우
  실제 PDF·Manifest 검증
    → 원문 구간 ID 선택으로 활동 자료 JSON/MD 구조화
    → Q0 5개 + 대체 5개 생성·독립 전제 검수·실제 TTS
    → 해시 검증을 마친 완성 은행만 원자적으로 게시

면접 시작 전·카운트다운
  검증된 Q0 은행 읽기(LLM/TTS 호출 0)
    → 장치 확인·카운트다운 동안 같은 준비 작업 공유
    → 승인된 음성 10개 선행 다운로드
    → 카운트다운 이후 실제 playing에서 질문 공개·타이머 시작

답변 확정 후
  같은 묶음의 확정 답변·정정·부정 + 원래 질문 요구
    → 명백한 무응답/사과/미완성 파편: 모델 0회
    → 그 외: 단일 코어 모델 최대 1회
       ├─ 충분: 준비된 다음 Q0 선택(추가 생성·TTS 0)
       ├─ 실제 확인점 있음: 답변 인용 + 제한된 단일 요구 문형으로 F
       └─ 불명확: 승인된 같은 질문을 비평가 재제시
    → 연결 음성과 필요한 F 음성 준비 병렬화, 실제 재생은 순차

종료 후
  확정 전사·실제 재생 장부·관찰 수치 저장
    → 기존 종료 평가 비동기 호출
    → 원문 인용 검증·앵커 산식·묶음/회차 집계·결과 저장
```

‘정확히 세 에이전트가 항상 최적’이라는 일반 법칙을 구현 근거로 삼지 않았다. 이 앱에서는 로그로 확인한 직렬 대기와 중복 생성이 병목이므로 위 세 단계로 나눴다. 독립적인 준비 작업과 음성 준비는 병렬화하고, 최종 전사가 필요한 의미 판단과 그 판단에 의존하는 작업의 순서는 보존한다. [OpenAI 공식 지연 최적화 문서](https://developers.openai.com/api/docs/guides/latency-optimization)의 호출 수 축소·독립 작업 병렬화 원칙을 참고했다.

### 사전 활동 자료

- `data/prepared/activities.json`, `activities.md`에 검증된 17개 **발췌 단위**를 저장한다. 17개 독립 활동으로 단정하거나 임의로 병합하지 않는다.
- 개인 행동·공동 행동·선택 이유·성과·수치·교사 관찰을 분리한다. 제공된 발췌에서 관찰되지 않은 필드는 unknown으로 남긴다.
- 모델이 인용문을 새로 타이핑하는 대신 서버가 고정한 원문 span ID를 선택한다. 원문·발췌 offset·PDF offset은 서버에서 복원·대조한다.
- 필드 의미·행동 귀속의 적절성은 모델 판단이고, 정확 인용과 같은 보장은 아니다. 교사의 평가 문장을 학생이 설명한 행동으로 대신 쓰지 않는다.
- 실제 최종 생성 1회는 28.175초였고, 동일 자료 재실행은 API 0회였다. 앞선 직접 인용 복사 방식의 실패 두 번·4호출도 보존했다. 이번 전체 실험의 실제 추출 호출은 총 5회다.

### Q0·음성 은행

- 공식 12분에 맞춘 서비스 정책의 Q0 5개와 슬롯별 대체 5개를 준비했다. 공식 문항 수를 5개라고 주장하지 않는다.
- 독립 전제 승인 10개와 실제 MP3 10개·521,640바이트를 검증했다. 첫 준비에서 PROCESS 대신 선택 기준을 묻던 대체 질문은 차단했다. 승인된 9개를 재사용하고 해당 후보만 재개해 완성했다.
- 원천 파일·발췌·규칙·지원처·질문 계획·활동 캐시 digest·모델·실효 목소리/속도·질문/음성 해시를 대조한다. 준비 중인 파일이나 손상된 후보를 완성본으로 사용하지 않는다.
- 런타임은 검증된 은행만 읽는다. 은행이 없으면 실시간 생성 체인으로 우회하지 않고 사전 준비 필요 상태를 반환한다.
- 회차·슬롯 기준으로 primary/대체를 선택하고 실제 앞선 질문과 중복되면 다른 승인 후보를 확인한다. 질문 UUID·부모 묶음·F 상한·목소리는 서버가 소유한다.

### 단일 코어와 맥락

- 의미 판단과 후속 초점 선택을 한 응답에서 함께 받는다. 모델의 내부 SDK 재시도는 0이며, 실패를 추가 모델 호출로 덮지 않는다.
- 같은 묶음의 Q0·재질문·F의 확정 원문과 ID, 정정·부정·불확실성을 함께 제공한다. 최신 짧은 구절이 앞선 설명을 대체하지 않는다.
- “같은” 같은 미완성 표현과 “백금입니다” 같은 짧은 유효 답변을 구분한다. 길이만으로 답변을 무효화하지 않는다.
- 질문이 요구한 근거·선택 기준·한 단계·본인 행동 등에서 실제 남은 지점만 선택한다. 전체 STAR나 추가 수치·성과·전공 연결을 사후 요구하지 않는다.
- 인용 선택지는 답변 앞부분에만 치우치지 않게 전체 발화와 끝의 정정 부분을 포함한다. 기록 자료를 이번 답변의 충족 근거로 대신 사용하지 않는다.
- 실시간 F는 모델이 자유롭게 사실 전제를 만드는 문장이 아니다. 현재 확정 답변의 실제 인용과 허용된 단일 요구 문형으로 구성하고, 실제 `ANSWER_TURN` ID·인용·offset·원래 요구·같은 root를 검사한다. 검수 방식은 `constrained_answer_follow_up`으로 표시하며 독립 의미 검수를 했다고 표시하지 않는다.
- 승인된 문장의 재제시는 해시·규칙·원천·의도·단일 요구를 다시 대조한다. F 재제시도 이전 확정 답변의 인용과 문형을 대조한다. 인사만 독립적으로 제거한 경우 변환 정보와 offset 이동을 기록해 재인사를 막는다.
- 모델 실패는 `unassessed`와 내부 failure code로 남긴다. 실패를 학생의 낮은 답변 품질이나 무응답으로 바꾸지 않는다.

## 3. 채점·저장과 안정성

종료 평가는 대화 밖에서 수행한다. 기존 I/A/S/R/C 앵커와 실제 답변 인용 검증을 유지하며, 묶음은 Q0만 100%, F1까지 70:30, F2까지 **70:15:15**로 집계한다. 제안의 `70:30:15`는 합계가 맞지 않아 적용하지 않았다. 보류 문항을 0점으로 채우거나 가중치를 재분배하지 않는다.

단일 코어의 origin·failure code·서버 보정·실제 분기·호출 수·소요 시간을 원문 전사·재생 이벤트와 함께 저장한다. Q0 사전 생성·전제 검수 시간은 offline 항목으로 보존하고 런타임 생성·검수 호출과 구분한다. 중복 요청·TTS 재시도는 같은 예약 턴·코어 결정을 재사용한다. 종료 후에는 이전 `/next` 캐시로 질문을 다시 반환하지 않는다.

기술적 STT 실패와 정상적으로 확정된 빈 전사는 구분한다. 실제 브라우저의 재생 장부 없이 질문이 제시됐다고 꾸미지 않는다. 원문에 없는 분석·시선·표정·합격 판단을 생성하지 않는다.

통합 시험에서 STT 실패 상태 보존의 간헐 실패를 발견했다. 과거 임시 로그만으로 그 단일 원인을 확정하지는 않았다. 확인한 코드 경계인 생성 중 동기 오류, 실패 후 늦은 확정/부분 전사, 이전 캡처 callback, 닫기 중 동기 오류에 고정 반례를 추가하고 캡처 소유권·터미널 상태·저장 후 알림으로 보완했다. 마지막 전체 자동 테스트는 **339/339 통과**했고 타입 검사·린트·프로덕션 빌드도 통과했다. 많은 PDF 재추출·서버 자식 프로세스가 한꺼번에 경쟁하지 않도록 일반 테스트의 파일 동시 실행은 4개로 제한한다.

## 4. 실측과 검증 범위

| 시험 | 관찰값 | 한계 |
|---|---|---|
| 실제 은행 로드·10후보 선택 | 네트워크/모델/TTS 호출 0. 마지막 load 521.4ms | 동시 작업 부하가 있는 단일 관찰이며 p95가 아님 |
| 새 서버 HTTP 준비 | 100ms, 런타임 LLM/TTS 0 | 장치·실제 재생 미사용 |
| 새 서버 HTTP 회차 생성 | 60ms, 승인 Q0·은행 identity·음성 유지 | 브라우저 카운트다운 전체 체감 시간 아님 |
| 합성 부분 답변 → F | 코어 1.675초, 실제 TTS 1.373초, MP3 준비까지 3.048초 | STT·브라우저↔서버 전송·실제 재생 제외. 공급자 API 왕복은 포함. 소수 사례 |
| 합성 충분 답변 → 다음 Q0 선택 판단 | 코어 3.154초, 모델 1회 | Q0 선택·브라우저 재생 시간을 포함하지 않음 |
| 미완성 파편 | 모델 0회, 1ms 미만 | 관찰 가능한 명백한 파편 분기 |

실제 모델이 “인터넷에서 자료를 찾아봤습니다”를 판단 근거가 충분한 답변으로 과통과한 실패 두 번을 별도 보존했다. 단순한 탐색 경로만 말한 경우를 좁게 확인하는 서버 검증으로 보정하고 `REQUESTED_BASIS_NOT_PROVIDED`를 기록했다. 최종 부분 답변 시험의 성공은 이 보정까지 포함한 결과다. 모델 자체의 정답률이 개선됐다고 계산하거나 정상 답변 전반의 정확도를 보장하지 않는다.

실제 HTTP 시험에서는 재생하지 않은 새 합성 시험 회차만 만들고 종료했다. `questionPresentations=[]`, 평가 분모 0, 회차 점수 null과 시험 provenance 저장을 확인했다. 기존 사용자 회차를 덮어쓰지 않았다.

## 5. UI 수정

- 별도 “이 면접 마무리하기”를 삭제하고 하단 종료 아이콘으로 통일했다.
- 답변 완료 버튼의 데스크톱 확대 규칙을 제거해 다른 주요 조작과 같은 작은 크기로 맞췄다.
- 장치별 고유 key를 보완하고 JSX의 key를 spread 앞으로 옮겼다. 실제 개발 브라우저에서 재현한 span key 경고가 수정 후 카메라·마이크·스피커 메뉴를 열 때 새로 발생하지 않음을 확인했다.
- 모핑 바깥 크기를 유지하면서 두 표면의 회전을 한 부모로 묶고 내부 원을 43%→52%로 키웠다. 기본 회전 주기는 8초→7.2초로 조금 빠르게 했다. 시작 전 정지·호버 재개·색 전환·마우스 이탈 시 정지·무음 동작과 접근성의 reduced-motion 설정은 유지한다.

## 6. 제안에서 구분해야 할 부분

- **0초 대기·0.1초 반응은 보장하지 않는다.** STT 확정, 모델 추론, 음성 준비, 전송과 실제 재생에는 시간이 걸린다. 위 숫자는 해당 구간의 실측값이다.
- 기본 브릿지를 STT 확정 전에 “잘 들었다”고 재생하지 않는다. 정상 무응답·실제 인식 오류·불완전 발화를 구분하고 내용 없는 고정 멘트를 매번 반복하지 않는다. 짧은 키워드 반응은 단일 코어 결정과 서버 문형 안에서 처리한다.
- 사용 중인 CLOVA Voice Premium의 공식 계약은 MP3/WAV 바이너리 응답이다. 현재 코드는 완성 MP3 캐시와 음성 준비 병렬화를 사용하며 첫 조각부터 발화하는 TTS 스트리밍을 구현했다고 표시하지 않는다. [CLOVA Voice Premium 공식 API](https://api.ncloud-docs.com/docs/en/ai-naver-clovavoice-ttspremium)
- SQL·학생 계정·업로드와 새로고침/서버 재시작 후 자동 회차 복원은 이번 구현에 포함되지 않는다. 로컬에 상태가 저장되는 것만으로 완벽한 복원이 되지는 않는다.
- 사후 평가는 기존 비동기 평가 경로다. 세 번의 별도 채점·재채점 LLM 호출이나 묶음별 병렬 채점을 이번에 추가하지 않았다. 인용이 점수를 의미상 지지하는지 독립 검증하는 P0-4 과제는 남아 있다.
- 실제 사용자의 긴 면접, 다양한 부분·모순·정정·엉뚱한 답변에 대한 사람 면접관 합의 평가는 계속 필요하다. 제한된 질문 문형의 자연스러움·다양성도 다음 실사용 로그에서 검토한다.

## 7. 실행

`start server.bat`는 자료 준비 후 활동 구조화와 Q0 은행을 확인한다. 동일 원천·규칙·설정의 유효 캐시는 재사용한다. 처음 준비하거나 자료·규칙·모델·목소리가 달라지면 사전 작업이 더 걸릴 수 있다.

```text
npm run prepare:context
npm run verify:context
npm run prepare:activities -- --run-live
npm run prepare:interview -- --run-live
npm run prepare:interview -- --check
npm test
npm run typecheck
npm run lint
npm run build
```

실제 API를 쓰는 사전 준비는 `--run-live`로 명시한다. 일반 자동 테스트는 격리된 provider를 사용한다. 화면은 새로고침하고 새 회차를 시작하면 새 준비 캐시와 단일 코어 계약을 사용한다.
