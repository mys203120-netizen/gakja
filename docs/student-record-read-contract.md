# 학생 화면 조회 계약

## 초기 화면과 집계

- `/api/bootstrap`은 계정, 현재 지원처, 현재 발행 자료 한 판, 환경설정, 현재 자료의 읽기 위치, 전체 이력의 숫자 요약을 반환한다. 과거 답변 본문·채팅 맥락·면접 리포트 JSON·복습 이력은 초기 응답에 넣지 않는다.
- 진행 중 면접은 최근 이력의 페이지 제한과 독립적으로 조회한다. 지원처·면접 방식별 최근 활성 세션과 현재 질문/활동 요약만 앱 틀에 포함한다. 이전 활성 면접도 이력 페이지와 ID 상세에서 접근 가능하다.
- 전체 건수는 `readStudentModel(studentId,'shell-counts','v1',...)`로 집계한다. 원본 기록의 수정·무효화·삭제·설정 변경에 대응하는 DB revision으로 재생성하며, 따뜻한 조회에서는 전체 이력을 다시 읽지 않는다.
- 현재 발행 자료는 이력 수에 비례하지 않는 하나의 콘텐츠 버전이다. 해당 자료의 문항별 작성 여부는 `kind=answers&view=state`에서 본문 없이 별도로 조회한다.
- 오늘 계획·준비 현황은 기록 목록의 최근 30개로 계산하지 않는다. 전체 유효 기록에 기반한 서버 집계를 사용하며, 여러 지원 학교가 공유하는 하루 학습 시간의 재배분도 해당 집계 갱신의 대상이다.
- 학습 세션의 초기 요약·캐시는 `weakPoints`·`resolvedPoints`·`independentlyVerified.questions`를 우선순위/최근순 최대 30개로 전달하고, 전체 수는 `weakPointCount`·`resolvedPointCount`·`independentlyVerified.count`로 보존한다. 과거 문항·자료 버전이 늘어도 초기 응답은 커지지 않으며, 개별 이력과 원래의 확정 리포트 상세는 그대로 조회할 수 있다.
- 같은 원본 revision의 오늘 훈련과 준비 현황은 하나의 training projection을 읽는다. 원본 변경 후에는 전체 유효 제출에서 다시 집계한다. 화면에 전달하는 보완 근거 ID는 질문당 최대 30개와 별도의 전체 건수를 사용하며, 전체 요청·근거 이력 자체는 삭제하지 않는다.
- 캐시의 조회 범위는 형식 버전과 함께 SHA-256으로 고정 길이 키를 만든다. 지원처·계획이 많아져도 DB 인덱스 키 크기를 넘지 않는다. 14일 이상 재생성하지 않은 파생 캐시는 다음 생성 시 정리하며 원본 기록으로 다시 만들 수 있다. 면접 타이머 heartbeat와 답변 초안만의 변경은 학습 요약을 무효화하지 않는다.

## 목록과 상세

`GET /api/student-records?kind=...`의 종류:

| kind | 목록 | 상세 |
| --- | --- | --- |
| answers | 답변 ID·질문·revision·작성 여부 | `questionId` 또는 `id`: 답변 본문 |
| interviews | 상태·지원처·훈련 종류 등 요약 | 면접 실행 상세는 기존 `/api/interviews?id=...` |
| reports | 리포트 ID·면접 ID·종류 | `id`: 전체 리포트와 소유 면접 요약 |
| memory | 항목·자가 점검·시각 | `id` |
| threads | 제목·지원처·보관 여부 | 대화 상세는 기존 `/api/chat?threadId=...` |
| notifications | 알림 30개 | `id` |
| briefings | 발행된 제목·분야 | `id`: 공개 범위가 일치하는 기사 본문 |
| confirmations | 사실 확인 기록 | `id` |
| assignments | 과제 제목·상태·항목 수 | `id`: 당시 문항의 공개 projection·최종 제출·이벤트 30개 |

- 목록 기본 30개, 최대 50개. `items`와 `page:{nextCursor,hasMore,limit}`를 반환한다.
- 커서는 불변인 `(created_at DESC,id DESC)`와 첫 페이지의 앵커를 담는다. DB 마이크로초를 보존해 밀리초 반올림으로 같은 시각의 행을 놓치지 않는다.
- 커서 범위에는 로그인한 학생, 종류, 지원처, 자료 종류·버전, 보관 상태, 과제 상태 필터가 포함된다. 범위가 다른 커서는 400으로 거절한다. 모든 실제 조회에는 서버 세션의 학생 소유 조건을 별도로 적용한다.
- 첫 페이지 뒤에 새 기록이 생겨도 기존 페이지의 앵커가 유지된다. 제목·답변 수정은 생성 시각을 바꾸지 않으므로 이전/다음 페이지 경계가 움직이지 않는다.
- `targetId`, `sourceVersion`은 면접·대화·리포트 목록에서 지원한다. 지원처는 학생 소유 여부를 먼저 확인한다. 과거 기록 상세는 최근 목록에 포함되지 않아도 ID로 열 수 있다.
- `sourceType=common`의 버전은 동결한 질문의 `common_revision`, 개인 자료는 `content_version`으로 구분한다. 공통 질문 버전과 개인 교재의 같은 번호를 동일한 근거로 간주하지 않는다.
- 과제의 `state=active|completed|all` 필터는 페이지 제한보다 먼저 적용한다. 오래된 미완료 과제가 최근 완료 과제 30개 뒤에 가려지지 않는다. 과제 ID 상세는 최근 overview 목록을 찾는 방식에 의존하지 않으며, 당시 발행본과 기존 `safeAssignment`의 정답 숨김 처리를 사용한다.
- v1 호환 API도 목록/상세 계약을 사용한다. 리포트나 답변 하나를 열기 위해 bootstrap을 호출하지 않는다.
- 채팅 활성 목록·보관함, 면접 목록도 같은 커서 계약을 반환한다. 80개 상한 뒤에 기록이 영구히 감춰지는 방식은 사용하지 않는다.

## 클라이언트 상태

- `useRecordPages`와 `useRecordDetail`은 학생 ID와 조회 범위를 상태 키에 포함한다. 이전 계정·지원처 응답이 늦게 도착하면 폐기한다.
- 불러오는 중, 실패, 실제 빈 목록을 별도로 표시한다. 아직 조회하지 않은 빈 배열을 ‘기록 없음’으로 해석하지 않는다.
- 답변 편집기는 질문별 원본 본문과 revision을 조회한 뒤 마운트한다. 기존 답변을 불러오기 전에 빈 답변 자동 저장을 시작하지 않는다.
- 리포트와 브리핑 상세는 ID 단위로 조회한다. 준비 자료 패널에서 여는 브리핑도 별도 상세를 조회한다.
- 설정 저장·지원처 변경·알림 읽음 때문에 전체 답변/리포트가 재전송되지 않는다. 앱 틀 새로고침은 위의 제한된 초기 계약만 갱신한다.
- 초기 환경설정은 화면에 필요한 키만 허용 목록으로 조회한다. 보완 판정·진단·메모·답변 의미 확인 등의 누적 이력은 포함하지 않는다. 실제 학습 시간 설정과 휴무 날짜는 설정 화면의 별도 조회를 사용한다.
- 학습 기록의 주기적 새로고침은 사용자가 이미 불러온 이전 페이지를 유지한다. 상세와 답변 비교에는 독립적인 로딩·오류·재조회 상태가 있다.

## 월간 캘린더

- `/api/planner?month=YYYY-MM`은 해당 월의 달력 격자와 선택 가능한 주간 행에 필요한 날짜 범위만 조회한다. `history=1`도 날짜 범위를 유지한다. 월 이동은 새 범위 요청으로 연결하며, 과거 월도 동일한 방식으로 열 수 있다.
- 표시할 계획과 연결된 완료 면접 ID만 확인한다. 과거 전체 계획·전체 완료 세션 ID를 초기 조회하지 않는다.
- 월별 표시용 근거는 답변 본문 없이 날짜·질문/활동·지원처·자료 종류/버전·계획 ID별 마지막 유효 기록으로 묶는다. 여러 세션으로 재시도해도 같은 계획의 근거가 무한히 늘지 않는다. 가져온 기존 학습 이벤트도 포함한다.
- 수동 계획은 생성 이후의 후속 연습도 인정한다. 예를 들어 9월 계획을 10월에 연습했다면 9월을 열었을 때 해당 사실을 유지한다. 원본 답변 무효화·질문 범위 변경은 과거 달력에서도 다시 반영한다.

## 전체 내보내기

- 사용자가 내보내기를 누르면 `/api/student-records/export`가 JSON을 스트리밍한다.
- 답변은 전체 canonical version을 250개씩 끝까지 순회한다. 학습 이벤트·가져온 이전 학습 이벤트(`importedStudyHistory`)·학습 리포트·면접 리포트·면접 요약·암기 이력도 소유 범위에서 250개씩 순회한다.
- 화면 목록에 불러온 30개만 내보내지 않는다. 서버는 한 페이지씩 보관하며, 소유 조건·스냅샷 앵커·불변 생성 시각/ID 경계를 유지한다. `study_sessions`의 생성 기준은 `started_at`이다.

## 검증 기준

1. 동일 시각 기록 75개를 30/30/15개로 이어 읽으며 중복·누락이 없어야 한다. 중간 새 기록·답변 수정에도 기존 커서는 안정적이어야 한다.
2. 학생·지원처·버전·보관 상태가 다른 커서를 거절하고, 오래된 ID 상세도 소유자에게만 반환해야 한다.
3. 답변 503개를 내보내면 503개가 남아야 한다. 모든 원본 쿼리는 학생 소유 조건을 가져야 한다.
4. 요청 도중 학생·지원처를 바꾸면 늦은 응답이 현재 목록으로 들어오지 않아야 한다. 더 보기 연속 클릭은 한 요청으로 처리한다.
5. 100/1,000/10,000개 이력에서 초기 응답 바이트, DB 반환 행 수, 응답 시간, 쿼리 계획을 측정한다. 최초 집계 비용과 revision이 같은 반복 조회 비용을 나누어 기록한다.

## 로컬 PostgreSQL 측정 기록

`node --import tsx tests/record-query-performance.mts`는 무작위 전용 스키마에서 실제 bootstrap·목록·revision cache 코드를 실행한다. 기존 계정·운영 테이블은 변경하지 않고 종료 시 해당 스키마만 삭제한다. 다음은 현재 발행 자료가 없는 합성 학생에게 답변/면접/리포트를 각각 해당 수만큼 넣은 실행 결과다. JSON은 압축 전 크기이며, HTTP 전송·브라우저 렌더링 시간을 포함하지 않는다. 반복 조회 7회의 작은 표본으로 운영 지연 시간을 보장하지 않는다.

| 각 이력 수 | 초기 JSON | 최초 집계 포함 | 반복 조회 중앙값 / 최대값 | 반복 DB 반환 행 | 목록 DB 반환 행 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 100 | 1,451 bytes | 25.52 ms | 2.69 / 3.28 ms | 6 | 31 |
| 1,000 | 1,453 bytes | 18.44 ms | 3.63 / 4.52 ms | 6 | 31 |
| 10,000 | 1,455 bytes | 36.31 ms | 6.72 / 7.00 ms | 6 | 31 |

목록은 DB에서 31개를 읽어 다음 페이지 유무를 판단하고 화면에 30개를 반환한다. 반복 초기 조회에서 전체 건수 집계 SQL이 실행되지 않는 것도 확인한다. 최초 집계와 원본 변경 뒤의 재생성은 전체 이력을 반영하므로 해당 DB 집계 비용까지 상수라고 주장하지 않는다.

같은 격리 실행에서 실제 DB 트리거로 답변 정정·삭제, 도움 사용 정정, 알림 읽음이 cache epoch를 바꾸고 재집계하는지, 답변 초안만의 변경은 cache를 무효화하지 않는지 검증한다. 공통 질문 7판과 개인 교재 7판을 나누는 SQL, 오래된 미완료 과제를 상태 필터로 찾는 SQL도 실행한다.

`node --conditions=react-server --import tsx tests/training-read-model-api.mts`는 실제 전체 답변 집계도 별도로 확인한다. 같은 활동의 유효 제출을 100/1,000/10,000개로 늘려 누적 횟수가 정확한지 확인하고, 원본 무효화 뒤 재계산·1만 개 보완 요청의 화면 요약 상한·재발행 뒤 이전 진단 배제·긴 캐시 범위 키·파생 캐시 보존 기간을 검사한다. 다음은 동일 로컬 환경의 5회 반복 조회 표본이며 HTTP·브라우저 시간은 제외한다.

| 같은 활동의 제출 수 | 내부 훈련 요약 | 최초 재집계 | 반복 조회 중앙값 / 최대값 | 반복 DB 쿼리 / 반환 행 |
| --- | ---: | ---: | ---: | ---: |
| 100 | 6,861 bytes | 213.86 ms | 2.73 / 3.24 ms | 6 / 4 |
| 1,000 | 6,864 bytes | 98.04 ms | 1.34 / 1.82 ms | 6 / 4 |
| 10,000 | 6,867 bytes | 686.02 ms | 0.97 / 1.65 ms | 6 / 4 |

원본 전체를 다시 읽는 최초 집계는 이력 크기와 실행 환경의 영향을 받는다. 반복 조회에서는 답변·이벤트·발행 원문 쿼리가 실행되지 않는 것까지 확인한다. 자동 보완 요청의 판정도 질문별 정규화·ID 조회·시점 이후 성공의 이진 탐색을 재사용한다. 1만 개 요청의 과거 이력을 버리지 않고 해결·재활성화를 재현하는 검사는 `training-review-performance.test.ts`에 있다.
